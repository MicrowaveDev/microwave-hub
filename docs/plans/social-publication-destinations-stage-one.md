## Требования и границы

Подтверждено пользователем:

- Общий каталог назначений хранится на node. Локальные credentials остаются в client.
- Новая задача однозначно определяет аккаунт и место исполнения.
- Реализуется только минимальный первый этап: каталог, привязка клиента и назначение в новых задачах.
- В Girls используется **селектор групп соцсетей**, без чекбоксов выбора назначений.
- Для первого этапа пользователь подтвердил сохранение нынешних вариантов селектора: отдельные сети и Twitter + Bluesky + Discord + Telegram. Дальнейшие группы и способ их настройки определяются позднее.

Предлагаемые технические решения этого плана:

- Одна новая таблица назначений и существующая `PublicationJob`.
- Один исполнитель на назначение; отдельная таблица исполнителей не нужна.
- Серверный режим предусмотрен в модели, но серверные назначения нельзя включить для отправки без отдельного этапа реализации worker/адаптеров.
- Новая версия контракта сосуществует с legacy jobs/receipts; миграция старой очереди не является условием первого этапа.

Не входят: серверный worker, перенос credentials, автоматический fallback, heartbeat/online-статусы, capabilities framework, вторая очередь, автоматические повторы неизвестной отправки, редактор групп соцсетей и изменение существующих исторических публикаций.

## Исходное состояние

- Girls создаёт private queue group и передаёт network-only destinations; версия receipts 2/3 не фиксирует аккаунт. См. `microwave-girls/app/services/localPublicationBridge.ts`.
- Список сетей и комбинированный вариант заданы в `microwave-girls/frontend/components/SocialPublishing/networks.ts`; форма — `SocialPublishDialog.vue`.
- Client хранит локальные аккаунты и `queueSources`: группа → соцсеть → аккаунт. См. `geesome-client/src/storage.js`, `queue-sources.js`.
- Client передаёт accounts/routes при claim. Node привязывает непривязанный job к маршруту в момент захвата. Зарегистрированной идентичности устройства в этом контракте нет.
- `geesome-node/app/modules/localClient/{models,index,outbox,producer,api}.ts` содержат очередь и её контракт.
- `socNetAccount` — отдельное серверное хранилище аккаунтов. Запись в нём не доказывает готовность к публикации; часть интеграций используется для импорта.
- План `geesome-node/docs/plans/local-social-publishing.md` исключал registry для исходного MVP. Новый этап явно расширяет эту границу; при реализации обновить соответствующий раздел.

## Минимальная модель

Добавить `PublicationDestination` в существующий node-модуль `localClient`:

| Поле | Назначение |
| --- | --- |
| `id`, `userId` | Стабильный ID назначения и владелец |
| `network`, `label` | Соцсеть и отображаемое название |
| `executionMode` | `client` или зарезервированный `server` |
| `clientId`, `localAccountId` | Локальный исполнитель и его аккаунт |
| `sourceGroupId` | Необязательная привязка к private group-источнику; чужие группы не участвуют в разрешении selector |
| `socNetAccountId` | Приватная ссылка серверного режима; пока не используется |
| `target` | Конечный канал/chat/campaign и другие параметры назначения |
| `enabled` | Разрешение новых задач и исполнения |

Правила:

- Для client обязательны client/local account, серверная ссылка отсутствует. Для server — обратное; server в первом этапе не принимается для enqueue/claim.
- Один credential может обслуживать несколько назначений, например разные Telegram-каналы.
- Стабильный ключ локальной регистрации: owner + client + local account + стабильный локальный ключ назначения. Повтор регистрации обновляет ту же запись, а не создаёт новую.
- Локальный ключ назначения нужен отдельно от аккаунта: один бот может иметь несколько каналов. Переименование не меняет ID.
- В публичной для producer проекции — ID, network, label, executionMode, enabled и безопасные параметры назначения. Не выдавать credentials, внутренние ссылки на секреты или ключ подключения клиента.
- Удаление локального маршрута явно отключает его назначение. Частичный запрос регистрации не отключает другие записи автоматически.
- `clientId` и назначение не разрешается перепривязать другому владельцу/клиенту обычным обновлением метаданных.

В `PublicationJob` добавить nullable `destinationId` для совместимости. Для новой версии сохранять immutable снимок исполнения: client ID, local account ID, mode и разрешённый конечный target. Использовать существующие поля, где они подходят; не дублировать payload без необходимости.

Изменение названия допустимо. Изменение аккаунта/исполнителя/target влияет только на новые jobs. Отключение назначения блокирует claim его новых-format queued jobs, но не стирает очередь и не запрещает подтверждение уже захваченного результата. Исторические назначения не удалять физически.

## Контракт и поведение

Перед кодом согласовать точные схемы в `geesome-client/docs/geesome-node-contract.md` и node-плане. Пути ниже обозначают операции, а не окончательные URL:

1. Owner регистрирует client connection с отдельным ключом, ограниченным этим клиентом. Повторно использовать существующий механизм API keys; точный способ хранения привязки проверить до реализации. Самостоятельно переданный `clientId` не является доказательством полномочий. Ключ регистрации устройства и producer Girls не должны давать право представляться любым клиентом.
2. Client при сохранении настроек/подключении идемпотентно объявляет безопасные метаданные назначений и сохраняет node IDs локально. При временной ошибке повторяет регистрацию с теми же ключами. Нельзя создавать новые IDs для восстановления потерянного ответа.
3. Node отдаёт owner-scoped bounded список назначений. Никаких сетевых проверок соцсетей при чтении списка.
4. Compose новой версии принимает явные `destinationId`. Node проверяет owner, enabled, поддерживаемый client-режим и target; атомарно фиксирует маршрут в job.
5. Claim новой версии выводит client identity из авторизации и выбирает только jobs этого клиента. Переданный чужой account/client ID не расширяет права. Legacy ветка claim обязана исключать новые-format jobs, даже если строки аккаунтов совпадают.
6. Client сопоставляет job с локальным аккаунтом и отправляет frozen payload. Изменение текущего queueSources не подменяет маршрут уже принятой задачи. Удалённый/недоступный локальный аккаунт не заменяется другим автоматически.
7. Существующие атомарный claim, claim token, result/cancel и state machine сохраняются. Result остаётся привязанным к исходному claim; отключение назначения не мешает подтвердить уже выполненную отправку. Не расширять доступ к jobs другого владельца или клиента.

Для Girls ввести новую версию receipt/digest. Она связывает исходный контент с выбранными destination IDs и подтверждённым снимком маршрута; повтор всегда использует исходное намерение. Обнаруженное несовпадение назначения или маршрута — конфликт, а не повод заменить аккаунт.

Расписание интервалов новой версии рассчитывать по destination ID: два аккаунта одной сети не делят хвост очереди. По возможности сохранить текущий snapshot-based расчёт без отдельной системы резервирования; его ограничение по конкуренции явно документировать.

## Селектор групп соцсетей

Girls показывает один selector групп соцсетей. Пользователь не выбирает назначения чекбоксами. **Группа соцсетей в селекторе не равна private GeeSome group, где хранятся источники очереди.**

Архитектурная граница: выбранная группа соцсетей разрешается в конкретный набор destination IDs до эффектов enqueue. Этот набор фиксируется в receipt, поэтому изменение состава группы позднее не меняет повтор исходной операции.

На первом этапе:

- Не создавать таблицу групп соцсетей, CRUD, редактор, пресеты или произвольные значения состава без решения пользователя.
- Не считать текущий статический комбинированный пункт окончательной моделью групп.
- Разделить загрузку каталога назначений и разрешение выбранной группы. Для согласованных текущих вариантов требуется одно enabled client destination на сеть; неоднозначность блокирует новый запрос.
- Для backend/integration тестов использовать явно заданные тестовые группы; это не продуктовая настройка.
- Текущие варианты selector согласованы пользователем при запуске реализации. Их можно включить после проверки node/client; новые группы без отдельного решения не добавлять.
- Перед эффектами нового запроса проверять весь набор назначений. Сохранить существующее поведение частичного успеха нескольких compose-вызовов и recovery по исходным ключам, не вводя распределённую транзакцию.

## Порядок и рабочие потоки

Зависимости: контракт → node foundation → client registration/worker → Girls integration → совместная проверка. Серверный worker остаётся отдельной будущей задачей.

| Поток | Вход и область записи | Результат / завершение | Зависимости и проверка |
| --- | --- | --- | --- |
| A. Контракт | Этот план; client contract docs; node local publishing plan | Согласованы schema, auth binding, vNext receipts и legacy gates; принято решение о группах до их UI rollout | Первый; ревью сценариев совместимости |
| B. Node | Контракт A; только node localClient, интеграция API keys, тесты и релевантные docs | Каталог, owner/client ACL, frozen destination jobs, безопасный legacy claim | После A; targeted API/DB concurrency/auth tests, node route/docs checks |
| C. Client | Контракт A, node B; только client storage/settings/queue-sources/worker/docs/tests | Стабильная регистрация, сохранение IDs, scoped claim, отсутствие передачи секретов | Локальный storage/settings можно делать параллельно B после A; интеграция после B; `npm run check`, `npm test` |
| D. Girls | Контракт A, node B, согласованные группы; bridge/dialog/network metadata/docs/tests | Selector групп, явные IDs, vNext receipts, интервалы по назначению | Подготовка receipt/tests может идти параллельно C; UI только после решения о группах; focused tests и repo Docker social flows |
| E. Интеграция | B/C/D и frozen fixtures; тесты/документы соответствующих репозиториев | Подтверждены изоляция клиентов, retries, legacy поведение, selector desktop/narrow | Последний; внешние отправки замоканы |

Все потоки запрещают изменения production credentials, живую публикацию, массовое изменение очереди и чужие рабочие изменения. У каждого потока ограниченная область записи; координатор отвечает за согласование контрактов и итоговую проверку. При делегировании передать исполнителю эту строку таблицы и актуальные локальные инструкции. Не запускать одновременное редактирование общих контрактных файлов.

Перед реализацией создать/найти tracking issues по правилам каждого репозитория. Выполнять Git workflow каждого репозитория; PR не сливать. Hub pointers обновляются только после появления нужных commits на соответствующих base branches.

## Совместимость и развёртывание

1. Определить production schema baseline. Новая таблица создаётся по node model-sync правилам; добавление колонок/индексов к уже развёрнутой PublicationJob требует применимой upgrade migration. Не полагаться исключительно на alter sync для production upgrade.
2. Сначала развернуть node с каталогом и двумя явно разделёнными версиями jobs. Новые jobs пока не создавать.
3. Обновить client, зарегистрировать отдельное подключение и назначения. Проверить их безопасный список и изоляцию claim.
4. После согласования групп включить новый Girls контракт. Старые request keys/receipts продолжают прежнее восстановление; их нельзя переинтерпретировать как новые назначения.
5. Старые queued jobs продолжают прежний контракт. Неоднозначные legacy jobs не получают destination автоматически. Историю, processing и needs_review не переписывать.
6. Не допускать одновременную работу старого и нового клиента над legacy очередью без явного операторского контроля. Новые jobs старому клиенту недоступны на стороне node.
7. При downgrade приложения, которое не понимает destination jobs, сначала остановить исполнение. Node downgrade при наличии таких jobs требует отдельной проверки: нельзя позволить старому claim забрать их как legacy. Сохранить rows/receipts; не удалять данные ради rollback.

## Проверка и критерии завершения

- [x] Повторная регистрация, перезапуск и потерянный ответ не создают новые назначения.

- [x] Интервалы независимы для двух назначений одной соцсети.

## Решения, которые остаются открытыми

- Будущие группы соцсетей и редактор их состава. Первый этап использует подтверждённые текущие варианты selector; новые группы не придумывать.
- Привязка ключа, URL, проекции и v4 receipt зафиксированы в `geesome-client/docs/geesome-node-contract.md`; для нового назначения используются существующие API-key IDs, отдельной таблицы клиентов нет.
- Production baseline проверен: released `publicationJobs` уже существует. Node migration `20261110000000-bind-publication-destinations.cjs` добавляет nullable поля с сохранением legacy rows и запрещает schema rollback при наличии destination jobs. Новая таблица назначений создаётся model sync.

Эти вопросы не требуют executor registry, heartbeat или универсального routing engine.

## Заметки реализации

При выполнении обновлять этот раздел: принятые решения, ссылки на issues/PR, обнаруженные ограничения, результаты проверок и оставшиеся задачи. Не оставлять значимые изменения контракта только в чате.

- 2026-11-10: сохранён план первого этапа; код и схема БД не изменены. Учтён selector групп соцсетей, решение об их составе отложено. Серверный worker исключён из этапа.
- 2026-11-10, выполнение: пользователь подтвердил сохранение нынешнего selector. На новом node его сети разрешаются только в однозначные включённые client destinations; отсутствие или несколько вариантов блокируют enqueue. Bridge API может принять явный ID на сеть. Редактор групп не добавляется.
- Контракт: существующий отдельный API key определяет `clientId=key:<id>`; clientId нельзя выбрать в теле запроса. Дополнительная таблица/схема ключей не нужна. Registry registration/list: `/user/local-publications/destinations`; scoped claim: `/user/local-publications/destination-claim`. Legacy claim исключает destination jobs.
- V4 digest: SHA256 от JSON `{version:4,destinationId,clientId,network,localAccountId,text,attachments:[{storageId,mimeType}],target}`; ключи target сортируются, порядок attachments сохраняется. Girls передаёт `producer.digest` в compose, node сверяет его до эффектов; job хранит frozen route. SFW aliases сохраняются в registry, но разрешаются и удаляются из конечного target до вычисления digest.
- Integration review: добавлена nullable `sourceGroupId` в назначение. Client объявляет группу своего маршрута; node проверяет владение/закрытость и соответствие compose; Girls не считает назначения других групп неоднозначными. Это сохраняет существующий выбор групп-источников без разбора технического localKey.
- Lifecycle review: owner может явно отключить назначение потерянного/отозванного ключа через `/user/local-publications/destinations/:destinationId/disable`. Перепривязки и автоматического восстановления доступа нет. При замене до 100 маршрутов client отключает удалённые и регистрирует новые порциями до 100 с исходными ключами.
- Girls tracker: https://github.com/MicrowaveDev/microwave-girls/issues/1029. Первые проверки: social CLI/bridge 64 теста, social UI 29 тестов, Generation Studio 889 тестов — PASS. Итоговые интеграционные проверки и delivery pending.
